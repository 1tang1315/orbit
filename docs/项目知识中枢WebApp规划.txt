# 项目知识中枢 · 方案整理

> 一句话：一个连接 GitHub 仓库、自动理解代码、主动沉淀知识、支持任务管理、可随时回顾的个人/团队「项目知识中枢」。
> 技术底座：DeepSeek Harness（一切皆插件）。

---

## 一、背景与核心痛点

- 现状：一个人同时接手多个项目，还有与别人协作开发的项目。
- 痛点 1（学不到东西）：读懂的东西（架构、坑、决策）没有沉淀，换项目/过段时间又得从头读。
- 痛点 2（留不下东西）：每次让 AI 分析、生成报告都是一次性会话，分析完就散了，没有变成可积累、可复用的资产。
- 痛点 3：技术栈反复搞不懂、反复问 AI。

## 二、核心目标：三层知识模型

| 层级 | 名称 | 生产方式 | 作用 |
|---|---|---|---|
| **L1** | 项目事实层 | 全自动生成 | 代码结构、架构图、提交历史、依赖、README/规范，随仓库更新 |
| **L2** | 个人理解层 | AI 起草 + 你确认 | 项目解析、架构理解、需求分析、规格/设计文档、踩坑经验、ADR、复盘报告 —— 这是「学到东西」的关键 |
| **L3** | 跨项目技术知识层 | 从 L2 提炼，长期复用 | 技术栈知识、通用经验/坑、模式模板 —— 这是「留得下东西」的核心 |

一句话定位：不是「GitHub 客户端」，也不是「普通知识库」，而是把「自动理解 + 主动沉淀 + 随时回顾」打通的**项目知识中枢**。

## 三、产品形态建议

- **不是纯 B 站 feed，也不是纯后台管理系统**。
- 主体：**知识库/资料库形态**（类似 Notion / Docs）＝「项目列表 + 每个项目的深度详情页（架构图 + 文档 + 提交 + 技术栈知识 + 复盘）」。
- 借鉴 B 站：首页放**项目动态流**（哪个项目最近有提交/新文档/更新推送）作为入口，不是用来「刷」。
- **设备策略**：
  - PC / Web 端＝**主阵地**（写作、深读文档、看架构图、AI 生成、编辑）。
  - 手机端＝**消费端**（看项目状态、读最新报告、收更新推送、碎片时间复习知识卡）。
  - 起步用 **PWA / H5 适配**，不优先做原生 App（一个人维护、多项目，原生双端太重）。

## 四、技术路线：由外部 MCP 驱动

本项目不内置 Agent Harness，也不依赖某个特定的 Agent 宿主。Web 应用负责展示知识与任务状态，外部 Agent 通过 MCP 读取、调用和修改：

| 路线 | 说明 | 结论 |
|---|---|---|
| A. 组装现成 | DeepWiki-Open + Obsidian 手动联动 | 可跑通但「一个入口看所有项目」体验割裂，只当原型 |
| B. 二开 DeepWiki-Open | 加项目维度 + 个人沉淀 + 移动端 | 可行，但底座要自己搭 |
| **C. 外部 MCP 驱动（采用）** | 应用提供稳定的数据与工具边界，Agent 在外部运行 | **不绑定宿主，调用与修改路径清晰** |

MCP 边界：模型、会话、调度和 Agent 主循环均在应用外部运行；本应用只提供 MCP Server 工具，由外部 MCP Client 发起读取、执行和修改请求。应用不需要安装或启动 Agent 宿主。

## 五、MCP 工具架构

**MCP 工具（核心增量，数量不多）：**
1. **GitHub MCP 工具** —— 按「Git 源适配器」列仓库、拉取提交/依赖/分支；私有仓库凭据由外部 MCP 服务管理；支持 webhook/调度触发重扫。
2. **代码分析与文档生成 MCP 工具** —— 输出架构图、技术栈检测、模块文档。
3. **知识沉淀 MCP 工具（L2）** —— 把「AI 分析 + 你确认」写成结构化 Markdown：项目解析、ADR、踩坑经验、复盘、需求/规格/设计文档。
4. **报告生成 MCP 工具** —— 生成汇报报告、需求分析、规格文档和设计文档。

**复用现成社区插件（省去自己写）：**
- 记忆/跨会话沉淀（L3）：由外部 MCP 记忆服务提供，本地优先、Markdown 原生、跨任务复用。
- UI 工作台 / Git 图 / 移动端：由本应用展示，数据和动作通过 MCP 获取与修改。
- 搜索/资料：由外部 MCP 搜索工具提供。
- RAG / 向量检索。

## 六、任务管理（与知识沉淀形成闭环）

**定位**：不是孤立「记待办」，而是把「执行」和「沉淀」连起来的飞轮——任务做完了，改动/经验/坑顺手落进知识库；知识库反过来指导下一个任务。

**闭环流程**：任务从哪来（GitHub issue/PR 导入 · 手动 · AI 规划）→ 任务看板（每项目一个）→ 通过外部 MCP 调用执行与定时任务 → 复盘沉淀（自动写改动摘要/ADR/文档）→ 知识库反哺任务规划。

**插件选型：**
- 每项目一个看板、跨会话保留：MCP 看板工具（按 workspace 隔离，持久化由服务端负责）。
- 五列看板 + 执行 + 定时：MCP 任务工具（状态通过工具回写，可跳转回溯外部执行轨迹）。
- 跨 branch/新会话计划：MCP 计划工具。
- 团队协作共享看板：MCP 团队工具。
- 子任务编排/工作流：MCP 工作流工具。

**需要自建的关键增量（2 小块）：**
1. 任务 ↔ GitHub issue/PR 双向联动。
2. 任务完成 → 自动复盘沉淀（改动摘要 + 踩坑 + ADR 落进 L2，提炼技术知识进 L3）。

## 七、扩展性：接入「自己的东西」

MCP 设计第一原则是边界清晰：**工具可替换、可组合，Agent 与数据应用解耦，不侵入 Web 核心**。

| 你想接的「自己的东西」 | 挂载的扩展点 | 方式 |
|---|---|---|
| 代码源：GitLab / Gitee / 自建 Git / 本地目录 | Git 源适配器 | 加一个源＝加一个适配器插件 |
| 模型：本地模型 / 公司 API / Ollama | 模型适配器 | 换一个模型适配器插件 |
| 已有笔记：Obsidian / 思源 / 内部文档库 | 数据源插件 | 统一检索进知识中枢 |
| 自建工具 / 脚本 / 内部系统 | MCP Server / Tool | 暴露为 MCP 工具，由外部 Agent 调用 |
| 自己的页面 / Tab / 面板 / 移动端 | UI 插件 | 随时加自己的视图 |

**关于 Obsidian 接入**：Obsidian 本质是本地 Markdown 文件夹（vault），最容易接入。
- 当知识源：做成数据源插件，统一检索 + 双向读写。
- 甚至**整个产品以 Obsidian 为知识层**：通过 MCP 读写本地 Markdown，不把 Agent 运行时嵌入 Obsidian 插件。

**两条宿主路线取舍：**

| 维度 | 甲：整个产品做成 Obsidian 插件 | 乙：独立 Web 为主体，Obsidian 当知识层 |
|---|---|---|
| 本地优先/数据归属 | 完美 | 好 |
| 移动端 | Obsidian 免费直接用 | 需自做 PWA/App |
| 知识图谱/双向链接 | 现成 | 需自建 |
| 对外汇报/展示漂亮页面 | 弱 | **强** |
| 团队协作 | 弱 | 强 |
| UI 自由度 | 受插件 API 限制 | 完全自由 |

两者可用 **Markdown 打通**：Obsidian 当「个人主战场」（沉淀/复盘/任务/项目知识），需要对外时再导出一份独立 HTML 报告/页面。

## 八、待决策问题（定案前需确认）

1. **核心用途**：主要给自己沉淀回顾，还是也要给团队/汇报对外展示？→ 决定「Obsidian 宿主 vs 独立 Web」。
2. **任务管理程度**：只管理自己多项目待办/进度，还是需要 GitHub issue/PR 双向同步（团队场景）？
3. **模型选哪家**：DeepSeek 官方 API，还是 OpenAI 兼容接口（如 GLM/Ollama）？→ 决定代码分析插件 model 配置。
4. **是否要「任务完成自动写复盘」**：强烈建议要（这是解决「留不下东西」的解药）。
5. **运行环境**：外部 MCP 服务是否可用；GitHub Token 由对应 MCP 服务管理（私有仓库多则必需，否则先接公开仓库）。

## 九、落地 MVP（三步）

1. **初始化**：配置外部 MCP Server 与客户端连接，启用 Git、任务、知识沉淀和报告工具。
2. **写 2 个自建插件**：`GitHub 接入（Git 源适配器）` + `知识沉淀/复盘`。
3. **接 1 个真实仓库**跑通：拉代码 → 出架构/文档 → 建任务 → 执行 → 自动复盘落库 → 手机端能看。
